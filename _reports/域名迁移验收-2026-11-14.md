# 域名迁移验收：301 现状与收尾（2026-11-14）

接 2026-11-12 的换域名（`bennetgreen-bilibili.github.io/…-Comparison-List.md/` → `https://termite-extant-isoptera.org/`）。
触发本轮排查的是 GSC 报的「网页未编入索引：重复网页，Google 选择的规范网页与用户指定的不同」。

结论先说：**这不是 canonical / hreflang 模板的 bug，是换域名的过渡期。** 旧地址被 Google 索引了约三周，
新域名对它是全新的；301 已经生效且逐字保留路径，Google 只是还没把信号迁过去。本轮做的是把
「301 到底覆盖到哪」实测清楚、把几条会拖慢收录的机械故障修掉、并把 301 变成 CI 里会报警的契约。

## 1. 301 现状（2026-11-14 实测）

旧域名是**整站级** 301（GitHub Pages 在 Settings → Pages 填了 Custom domain 之后的固定行为），
不是逐路径配置的规则——所以不存在「漏配某条 301」这种可能，路径原样带过去：

| 旧地址 | 结果 |
| --- | --- |
| `…/` | 301 → `https://termite-extant-isoptera.org/` |
| `…/list/` `…/stats/` `…/data/` `…/download/` `…/papers/` `…/search/` `…/blog/` `…/guestbook/` `…/changelog/` `…/list/name-issues/` | 301 → 新域名同一路径 |
| `…/species/mastotermes-darwiniensis/`（zh / en / es） | 301 → 同一路径 |
| `…/genus/mastotermes/` `…/family/termitidae/` `…/subfamily/termitinae/` | 301 → 同一路径 |
| `…/species/…/photos/` `…/assets/custom.css` | 301 → 同一路径 |
| `…/sitemap.xml` `…/robots.txt` `…/feed.xml` `…/search-index.json` | 301 → 同一路径 |
| `…/list/?utm_source=…&q=…` | 301，**查询串保留** |
| `…/does-not-exist-xyz/` | 301 → 新域名同一路径（该路径在新域名上 404，属正常） |

单跳，没有 301 套 301。新域名自己那侧的规整也都在：`http:` → 301 `https:`，`www.` → 301 apex，
去尾斜杠 → 301 加尾斜杠（`/list` → `/list/`）。

新域名抽查 40 个 URL（首页、列表、统计、数据、下载、论文、搜索、博客、留言、更新日志、名称问题、
三语物种页、属、科、亚科、RSS / Atom / JSON、Google 与百度的验证文件）：**全部 200，页面 canonical 全部指向自身，0 例外**。
`sitemap.xml` 11,291 条、0 条旧域名；`sitemap.txt` 11,289 行、全部新域名；`robots.txt` 在域名根，两条 `Sitemap:` 生效。

所以「设置 301」这件事在站点侧没有可再写的配置；剩下的只是让 Google 把旧 URL 重新抓一遍。

## 2. 本轮改动（3 处）

### 2.1 新增 IndexNow key 文件（站点根）

`e2e5803b0bdbaf2841439d61209ca404.txt`，内容就是这串 key。Jekyll 会把根目录的静态 `.txt` 原样拷进
`_site/`，部署后地址是 `https://termite-extant-isoptera.org/e2e5803b0bdbaf2841439d61209ca404.txt`。
协议要求 key 文件放站点根、内容与文件名主干逐字相同。 <!-- src:S0444 -->

### 2.2 修 `.github/workflows/indexnow.py`：提交其实一次都没成功过

原实现按文件名判 key 文件：`^[A-Za-z0-9-]{8,128}\.txt$`。根目录里的 `llms.txt`、`robots.txt`、
`sitemap.txt` 名字都不足 8 字符所以没撞上——**但只要有任何一个 8 字符以上的 `.txt`，脚本就会
`sys.exit("multiple <key>.txt files found")`**；而根目录从来没有真正的 key 文件，
`read_key()` 的第一条分支就是 `no <key>.txt file found`。CI 里这一步带 `continue-on-error: true`，
于是失败被静默吞掉，Bing / Yandex / Seznam / Naver 从建站起就没收到过推送。

现在改成：先按名筛候选，再要求**内容 == 文件名主干**才算 key 文件（协议本来就这么要求 <!-- src:S0444 -->），
只有真正合格的才参与「多个 key」判定。本地验证：

```
$ python .github/workflows/indexnow.py --dry-run
key file:    e2e5803b0bdbaf2841439d61209ca404.txt
urls:        11291
would POST batch 1/2: 10000 urls
would POST batch 2/2: 1291 urls
```

### 2.3 把 301 写成 CI 契约（`.github/workflows/pages.yml`）

部署后的线上校验原来只查 17 条新域名 URL 的 200 + 关键内容，现在多查 4 条旧域名 301
（首页、`/list/`、物种页、`/en/list/`）：状态码必须是 301/308，`Location` 必须逐字等于
`新域名 + 同一路径`（尾斜杠容忍）。这条变红只有三种原因：GitHub 改了旧地址的重定向行为、
有人在 Pages 设置里清掉了 Custom domain、或者 `_config.yml` 的 `base_url` 被改坏。

本地跑同一段脚本：17 条 200 检查 + 4 条 301 断言**全 OK**。

## 3. 需要人在界面上做的（这几步没有 API 可代跑）

### 3.1 Google Search Console（最要紧）

1. 属性：优先加「域名属性」`termite-extant-isoptera.org`（DNS TXT 验证，Cloudflare 里加 GSC 给的那条
   `_github-pages-challenge…` TXT）；也可以加「URL 前缀」`https://termite-extant-isoptera.org/`，
   用「HTML 文件」验证——`googleb89ba243d635e504.html` 已经在域名根、返回 200。
2. 提交 `https://termite-extant-isoptera.org/sitemap.xml`。
3. **设置 → 地址更改**：⚠️ 本项目旧站是 `github.io` 下的**项目子目录**，不是域名也不是子域，
   工具大概率不接受它当旧来源，详见 §7。不要为了凑这个工具去改站点结构——301 才是主信号。
4. 对报「重复网页」的那几条最重要的 URL 点「请求编入索引」（有每日额度，别一次刷完）。

预期：地址更改生效后 1–6 周，GSC 里旧 URL 从「重复网页」变成「已通过 301 重定向」；
在这之前重复网页继续出现是正常的，不用再改模板。

### 3.2 Bing Webmaster Tools

加站点并验证（可以直接从 GSC 导入），用 **Site Move** 把旧目录指向新域名，再提交 sitemap。
IndexNow 这边已自动化：本次改动包含 `.github/workflows/`，会触发 sitewide 判定，部署后 CI 自动全量推
11,291 条。

### 3.3 百度搜索资源平台

`baidu_verify_codeva-02OUrzqDJS.html` 仍在域名根、返回 200，属性不会掉。若站点已绑定，用「改版工具」
提交旧地址 → 新地址；再提交一次 sitemap（`sitemap.txt` / `sitemap.xml` 都行）。百度跟进 301 比 Google 慢。

### 3.4 Cloudflare（可选）

想把 `/index.html` 这种重复文件形式也收掉，可以加一条 Redirect Rule：
`http.request.uri.path eq "/index.html"` → 301 `/`。这条对本次问题没有影响（页面自己的 canonical
已经是目录形式），不做也行。**不建议**现在开橙云代理。

## 4. 部署（唯一剩下的机械动作）

本机没有 GitHub 凭据（`git push` 会要求输入用户名），所以这一轮改动只能提交、不能推：

1. `git push` → CI 跑全链 → `deploy` → `verify`（含新的 4 条 301 断言）→ `indexnow` 全量提交。
2. 部署完成后 2 分钟内 key 文件必须可访问；`indexnow.py` 会自己等它上线（12 × 10 秒），
   超时就 red。等不急可以手动补一次：`python .github/workflows/indexnow.py`。
3. 手工回归：打开 `https://bennetgreen-bilibili.github.io/-Extant-Isoptera-Latin-Name-Chinese-Name-Comparison-List.md/species/mastotermes-darwiniensis/`，
   应当立刻落到新域名的同一页。

## 5. 回滚

本轮三处改动都是加法：删掉 key 文件、把 `indexnow.py` / `pages.yml` 的两段改回去即可，
不影响线上 301，也不影响已有页面。

## 7. 「地址更改」工具：本项目大概率用不了

**结论：别在这个工具上耗时间。** 旧站 `https://bennetgreen-bilibili.github.io/-Extant-…-Comparison-List.md/`
是 `github.io` 域名下的**项目子目录**，而工具只把「域名」或「根网址前缀」当旧来源：

| 旧来源 | 能否当旧来源 |
| --- | --- |
| Domain 属性 `example.com` | 能 |
| 根 URL 前缀 `https://example.com/` | 能 |
| 带路径的 URL 前缀 `https://example.com/products/` | **不能** |
| `https://user.github.io/repo/` | **不能**（同上，且有路径；`github.io` 的 Domain 属性要 DNS 控制，拿不到） |

两个二手教程（S0445、S0446）都明确写了「这个工具只能用于域名级别的资源，不能用于目录」；
Google 官方 9370220 与 developers.google.com 在本网络超时，未能逐字核对，但工具适用范围本身就是
「从一个网域或子网域迁到另一个网域或子网域」，与二手教程一致。真要去看：旧属性的
**设置 → 地址更改**里若列表为空 / 目标选不到，就是这个原因，不是你没配好。

不用它也不影响结果：Google 对永久跳转的处理与「地址更改」通知共用同一套信号（301 + 新站 sitemap +
页面自指 canonical），只是慢一些、没有 180 天迁移记录可看。本项目这三样都已就位。

**不能省的两件事**（等价于工具的「保留 180 天」约束）：

- 旧仓库不能删、Pages 设置里的 **Custom domain 不能清**——那 28 条整站 301 就是这个配置产出的，
  一清就全断（`pages.yml` 的 4 条 301 断言会立刻变红）。
- 按 Google 建议，永久跳转保留一年以上；旧域名也别让人捡走。

**该用工具的地方**：Bing Webmaster 的 **Site Move** 接受 URL 前缀（含目录），本项目旧路径可以作为
源前缀提交，见 §3.2。
