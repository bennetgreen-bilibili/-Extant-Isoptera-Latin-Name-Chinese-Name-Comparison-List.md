# 换域名可行性评估（2026-11-12）

> 触发问题：「谷歌抓不到站点地图，想给网站换个域名，行不行？」
> 结论：**换域名可行、成本不高，但它不是这个问题的解药。** 站点的 sitemap 本身是健康的（见 §1），
> 抓不到几乎一定出在 Search Console 的「属性 / 提交地址」这一层。先花 10 分钟定位，再决定要不要迁。

---

## 1. 实测：sitemap 现在是好的

2026-11-12 用 Googlebot UA 直接抓线上（脚本见 §7），结果：

| 项 | 结果 |
| --- | --- |
| `…/-Extant-…-List.md/sitemap.xml` | **200**，`Content-Type: application/xml`，757,226 字节 |
| `<loc>` 条数 | **3,785**，全部同域、无重复、每条都带 `<lastmod>` |
| `…/-Extant-…-List.md/sitemap.txt` | **200**，`text/plain`，495,543 字节 |
| 抽样 3 个物种页 | 200，`text/html` |
| `https://bennetgreen-bilibili.github.io/robots.txt` | **404**（GitHub「Site not found」页） |
| `https://bennetgreen-bilibili.github.io/` | **404**（没有 user site 仓库） |
| `https://bennetgreen-bilibili.github.io/sitemap.xml` | **404** ← 注意这一行 |

规模也远在 Google 的限制内（单文件 ≤ 50,000 条 / ≤ 50MB），格式合规，不存在「文件太大读不动」。

**所以「谷歌抓不到」不是 sitemap 文件本身的问题。**

## 2. 那最可能是哪几种情况

按概率排序，每一种都有 30 秒内可验证的特征：

1. **提交的 URL 少了子路径**。在 GSC 里填成了 `https://bennetgreen-bilibili.github.io/sitemap.xml`——
   那条是 404（上表最后一行）。正确地址是
   `https://bennetgreen-bilibili.github.io/-Extant-Isoptera-Latin-Name-Chinese-Name-Comparison-List.md/sitemap.xml`。
   GSC 报错通常是「无法获取」/「一般性 HTTP 错误」。
2. **属性加错了层级**。GSC 只允许提交**本属性路径下**的 sitemap。如果属性是根域
   `https://bennetgreen-bilibili.github.io/`（它现在整站 404），sitemap 在子路径里，就会被判定为
   「属于其他网站」。正确属性是带子路径那一串，验证方式是页面里的
   `<meta name="google-site-verification">`（`index.md:13`、`en/index.md:13`、`es/index.md:13`）——
   那个 meta 只对子路径属性有效，能验证通过就说明属性没加错。
3. **提交时站点正好在重建**。GitHub Pages 部署期间短暂 404/5xx，GSC 那一次抓取失败会留下红字；
   重新提交一次即可，不影响后续。
4. **把「sitemap 状态」误读成「收录状态」**。这是最常见的误会：sitemap 读到了，也不等于页面会被收录；
   3,785 个 URL 的新站，Google 全量抓取+收录本来就要数周到数月（`robots.txt` 里也写了「Google 侧依靠
   sitemap + 站内链接 + 时间」）。

## 3. 换域名到底解决什么、不解决什么

**能解决的（真实收益）：**

- 站点从 `/<repo>/` 子路径搬到域名根：`sitemap.xml` 变成 `https://域名/sitemap.xml`，
  **根域 robots.txt 真正生效**（`robots.txt:51-52` 那两条 `Sitemap:` 指令现在是指向子路径的死指令，
  因为爬虫只读域名根；换成自定义域名后它们才第一次真正起作用）。
- GSC 可以直接建**域名属性**（DNS TXT 验证），不再受「子路径属性」那套路径归属限制。
- URL 变短、变干净。现在是 `/-Extant-Isoptera-Latin-Name-Chinese-Name-Comparison-List.md/`，
  开头一个连字符、结尾一个 `.md`——邮件/IM 里被当成文件截断、引用时难看，这些都会消失。
- 以后换托管（Cloudflare Pages / Netlify / 自建）时链接不用再变一次。

**不能解决的：**

- 如果病根是「提交错 URL」或「属性加错」，换成新域名后你照样会在新域名上重复同样的错。
- **国内访问速度**。自定义域名仍走 GitHub Pages 的 CDN，中国大陆的可达性不会因为换域名变好；
  要解决这个得换托管（方案 D）。
- 旧 `github.io` 链接的权重。GitHub 文档只承诺「apex 与 www 之间自动 301」（见来源 S0429），
  **没有承诺** `user.github.io/repo/` 会 301 到自定义域名——这一条必须迁移前用 `curl -I` 实测。
  不 301 也不致命：`_layouts/default.html:60` 的 canonical 已经指向新域名，Google 会合并，
  但更稳的是迁完后在 GSC 用「地址更改」工具。

## 4. 迁移工程量（这是可行性评估的核心）

配置是集中的，这是好消息；但硬编码不少，这是主要工作量。

| 位置 | 旧域名硬编码处数 | 处理方式 |
| --- | --- | --- |
| `dataset/data/**`（JSON-LD 等派生数据） | 6,882 | 跑 `build_dataset.py` 重生成，**不要手改** |
| 根目录 `sitemap.txt` | 3,783 | 跑 `build_sitemap_txt.py` 重生成 |
| 根目录其余 md / 模板 | ~456 | 逐处替换 + `check_liquid.py` |
| `en/**`、`es/**` | 393 + 393 | 逐处替换（如 `en/blog.md:19` 的手写绝对链接） |
| `_tools/`、`assets/` | 7 | 手改 |
| **合计** | **11,919** | 其中约 10,665 处是派生产物，脚本重算即可 |

真正的源码改动面：`_config.yml` 三行（`url`、`baseurl`、`base_url`，第 22/23/27 行）+ 约 1,250 处
绝对地址替换 + 全套派生脚本重跑。`site.base_url` 一个变量被 6,000+ 处模板引用，模板层本身不需要动。

**风险：中低。** 配置集中、派生脚本齐全、`check_site.py` / `check_liquid.py` 能兜住大部分断链；
主要风险是漏改硬编码（尤其 en/es）与派生数据没重跑导致 sitemap 里混入旧地址。

**时间：半天到一天**（含 CI 与人工抽查），域名注册与 HTTPS 证书签发另算（几分钟到 24 小时）。

**SEO 成本：现在≈0。** 站点 2026-10 才上线，公开搜索里还查不到本站，说明收录和外链都接近于零——
这正是迁移最便宜的时刻。如果已经有排名，换域名要 301 + 地址更改，恢复期通常 2–8 周。

## 5. 三条路线对比

| 方案 | 成本 | 解决什么 | 不解决什么 |
| --- | --- | --- | --- |
| **A. 只修 GSC 提交** | 10 分钟，0 元 | 属性/URL 错配导致的「无法获取」 | 根域 robots、URL 难看、绑定仓库名 |
| **B. 建 user site 仓库，放根 robots.txt** | 30 分钟，0 元 | `Sitemap:` 指令生效；根域不再 404，可放跳转页 | 子路径仍在，属性仍带子路径 |
| **C. 自定义域名（继续 GitHub Pages）** | ¥60–120/年 + 半天~1 天 | §3 全部真实收益 | 提交错 URL 依旧会错；国内速度不变 |
| **D. 换托管 + 自定义域名** | ¥60–120/年 + 1–2 天 | C 的全部 + 301 规则可控、国内可达性可能更好 | 构建流程要改，迁移面最大 |

## 6. 建议的执行顺序

1. **今天**：按 §2 的三条自查 GSC（属性完整 URL、提交的 sitemap 完整 URL、报错原文）。
   90% 的概率在这一步就解决了，且不需要碰域名。
2. **如果只是想让 `Sitemap:` 指令生效**：做方案 B，30 分钟，零成本，随时可撤。
3. **如果确定要长期运营这个名录站**（我倾向于「是」：有 Zenodo DOI、三语、3,785 页，值得一个正式域名）：
   走方案 C。**现在就做**——收录≈0 时迁移几乎零损失，越晚越贵。
4. 国内读者是主力的话，把 C 和 D 合并考虑：自定义域名 + Cloudflare Pages，一次到位。
